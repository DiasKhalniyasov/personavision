# The front page's slide sets, one per example test

A **slide set** is one generated person per slide, on one screen of one session, baked out of a
run directory by `pnpm bake:landing-slides` and never edited by hand (#427). This directory
holds the sets baked from the **example templates'** runs — the six real public sites offered on
the New test screen (`apps/viewer/src/screens/newtest/templates.ts`).

Which set `/` shows is decided in one place: [`../slideSets.ts`](../slideSets.ts). It lists the
sets in the order the page prefers them with the committed example run's set last, so that set
is the fallback and a template set is shown by being registered above it.

## What is here today

Nothing yet. The five curated sets #429 owes are blocked on the runs of **#423**, which need a
model key the API accepts. Until a run exists there is nothing to curate, and a template that
produced no outcome of its own gets no slide set rather than an invented one.

## Making a set

### 1. The runs

The template runs are made against live third-party sites and cost money, so they are not in
this repository and are never regenerated by a test:

```sh
pnpm acceptance:templates          # six people, one repeat, each template, into ~/.personavision/template-acceptance
```

See [`docs/template-acceptance.md`](../../../../../../docs/template-acceptance.md) for what it
costs and what it needs. Its table prints, per template, whether that run produced a
**contrast** — a session that reached the thing and a session that did not, and on which
viewports. That line is what to read first: a set needs both.

### 2. Which sessions

Six slides out of six people, chosen so that the contrast is the point and not hidden:

- at least one session whose outcome is **`success`** and at least one that is **not**, on the
  same task;
- at least one **phone** viewport and at least one **desktop** one;
- never an `automation_failure` — our own breakage is not a person's behaviour;
- each person on the **screen where their decision happened**, which is the screen index in the
  triple.

`pnpm open <run dir>` is the quickest way to find those screens: the Sessions screen lists every
session with its outcome, and a session's replay numbers its screens in walk order.

### 3. The bake

One command per template. `--assets` is what makes a set from a run outside this repository
loadable at all: it copies every capture the slides name into the app's own
`apps/viewer/public/landing-slides/<template id>/<run id>/…`, which is what Vite serves and what
`screenshotBase` resolves a slide against, and it records the triples and the captures' SHA-256
in `<template id>.bake.json` beside the set.

```sh
pnpm bake:landing-slides ~/.personavision/template-acceptance \
  apps/viewer/src/screens/landing/slides/stripe-testing-payments.json \
  --assets apps/viewer/public/landing-slides/stripe-testing-payments \
  <run id>:<session>:<screen> <run id>:<session>:<screen> …
```

The run directory's name is the run's id, and `pnpm acceptance:templates` prints the runs root at
the foot of its table.

### 4. Registering it

One entry in [`../slideSets.ts`](../slideSets.ts), above `EXAMPLE_SET`:

```ts
{
  id: 'stripe-testing-payments',
  site: 'docs.stripe.com',
  screenshots: assetsAt('/landing-slides/stripe-testing-payments/'),
  read: async () => (await import('./slides/stripe-testing-payments.json?raw')).default,
},
```

Nothing else on the page changes. `slideSets.test.tsx` then asserts that set the same way it
asserts every other: it parses, it shows both viewports and an outcome that is not a success, it
holds every capture it names, its record's triples match its slides and their hashes match the
committed bytes, and the front page renders it.

## What is committed and what is not

- **Committed**: the set, its `.bake.json` record, and the captures under
  `apps/viewer/public/landing-slides/`.
- **Not committed**: the runs. They live outside the repository, and `runs/` holds only the
  example run, which nothing here regenerates.
